# Bot & MCP Independent Lifecycle Implementation & Verification Matrix

## Overview

This document tracks the implementation and isolated verification of the approved Bot & MCP Independent Lifecycle separation plan (`feat/bot-mcp-independent-20261105`).

### Core Architectural Invariants

1. **Separated Process & Supervision Boundaries (`bot` vs `mcp`)**
   - `cdr-runtime.exe` runs the Discord bot runtime.
   - `cdr-remote-agent.exe` runs the standalone Remote MCP runtime (`ManagedRemoteAgent`) without requiring Discord credentials or initializing the bot database.
   - Explicit ownership mode (`CODEX_REMOTE_MCP_OWNERSHIP=embedded|external`, plus persistent ownership state in `.cdr-maintenance/mcp-ownership-state.json`):
     - `embedded`: Backward-compatible default when neither `CODEX_REMOTE_MCP_OWNERSHIP=external` nor `.cdr-maintenance/mcp-ownership-state.json` is present, ensuring existing pre-cutover installations are never silently flipped before the fenced transition; also used for explicit guarded manual rollback.
     - `external`: Target independent mode activated by explicit `CODEX_REMOTE_MCP_OWNERSHIP=external` or a committed `.cdr-maintenance/mcp-ownership-state.json` (`schema_version=1, mode="external", state="committed", committed=true`). In external mode (or if the ownership state file is unreadable, malformed, or held in `cutover_pending`/`cutover_failed_hold`), `cdr-runtime` skips embedded `ManagedRemoteAgent` creation, preserves `config.remote_mcp` for `!pro` only when external ownership is committed, consumes `bot_data/remote_mcp_status.json` fail-closed, and never auto-spawns an embedded connector when external MCP is down.

2. **Fail-Closed External MCP Status & `!pro` Readiness**
   - External MCP atomically writes a versioned status record (`schema_version`, `component`, `install_root`, `process_identity`, `executable_path`, `artifact_sha256`, `build_info`, `updated_at_ms: i64`, `heartbeat_at_ms: i64`, `connection_verified_at_ms: Option<i64>`, `device_id`, `bridge_fingerprint`, `hello_ack`, `ready`, `draining`, `generation`).
   - `ready` is immediately invalidated (`false` and `connection_verified_at_ms = None`) on the WebSocket transport close boundary (before slow worker/session cleanup), drain start, or shutdown start, with `mark_draining` and `mark_shutting_down` latched under a single publisher lock so delayed heartbeats or late `hello_ack` frames can never resurrect readiness.
   - Process liveness (`heartbeat_at_ms`) and active WebSocket bridge-connection liveness (`connection_verified_at_ms: Option<i64>`, updated only upon `hello_ack` or inbound frames in `serve_commands` via `status.record_bridge_inbound(generation)` when `receive_gateway_frame` returns `GatewayFrame::Message` from `Message::Text` or `GatewayFrame::ControlAck` from `Message::Ping`/`Message::Pong`, while `Message::Binary` is rejected with `BridgeError::UnsupportedBinary`) are tracked separately (`R3`). In `serve_commands` (`crates/cdr-remote-agent/src/bridge.rs`), outbound WebSocket `Ping` frames are sent every `DEFAULT_BRIDGE_PING_INTERVAL_MS = 1_500` ms (`1,500` ms, without refreshing `connection_verified_at_ms`) and an active session times out with `BridgeError::LivenessTimeout` after `DEFAULT_BRIDGE_LIVENESS_TIMEOUT_MS = 4_500` ms (`4,500` ms) without an inbound frame.
   - Bot `!pro` (`ProPromptRuntime::verify_external_mcp_ready` in `crates/cdr-runtime/src/pro_runtime.rs`), Tray status (`Get-McpTrayStatus` in `codex-discord-tray-runtime.ps1`), and cutover readiness (`Test-CdrExternalMcpCutoverStatusReady` in `scripts/CdrLaunchJournal.ps1`) all fail closed and verify all 17 fields of `ExternalMcpStatusRecord`: `schema_version`, `component`, `install_root`, `pid`, `process_identity`, `executable_path`, `artifact_sha256`, `build_info` (`schema_version`, `package_version`, `source_state`), `updated_at_ms`, `heartbeat_at_ms`, `connection_verified_at_ms` (mandatory non-null positive integer within `DEFAULT_EXTERNAL_MCP_STATUS_STALE_MS = 6_000` ms max age and at most `2,000` ms future skew relative to wall clock or `heartbeat_at_ms`), `device_id`, `bridge_fingerprint`, strict booleans (`hello_ack === true`, `ready === true`, `draining === false`), and `generation >= 1`, plus current bot configuration (`CODEX_REMOTE_MCP_ENABLED=1`, committed `external` ownership, and non-empty matching `DeviceId` and `BridgeFingerprint` with default TTL 1800s), live OS process matching exact `process_identity` (`<pid>|<dotnet_ticks>`), and executable artifact SHA256.
   - Reading status (`remote_mcp_status.json`, `Reason = 'matched_status'`) sets `HasControlAuthority = $false` and never grants start/stop/force-kill authority (`Reason = 'status_only_no_kill_authority'`). Likewise, legacy `.codex_discord_rust.runtime.lock` files grant `HasControlAuthority = $true` only when persisted ownership evidence (`startup.process_identity` via `Read-CdrRuntimeStartup` or `identity=<pid>|<ticks>`) matches the live process; missing or stale startup identity (`lock_startup_identity_mismatch`, `lock_identity_mismatch`, or `matched_legacy_lock_pid_only`) returns `HasControlAuthority = $false`. `Stop-CdrVerifiedProcess` retains the handle-pinned `System.Diagnostics.Process` object through verification and calls `$targetProc.Kill()` and `$targetProc.WaitForExit($WaitTimeoutMs)` (checking `$targetProc -is [Diagnostics.Process] -or $null -ne $targetProc.PSObject.Methods['WaitForExit']`).

3. **Detached Control Execution & Revisioned Last-User-Command-Wins**
   - Control helpers (`codex-discord-rust-watchdog.ps1`, `codex-discord-bot.cmd`, `codex-discord-bot-headless.vbs`, `codex-discord-rust-restart.ps1`, `scripts/CdrForceRestart.ps1`, `Invoke-CdrAppLaunch`, `Invoke-CdrJournaledProcessLaunch`) launched from either the Discord bot or an MCP terminal (`CapturedWindowProcess` with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) execute across a WMI (`Win32_Process.Create`) detached boundary outside the caller's process tree and job object while preserving the caller's Windows `SessionId`, `UserSid`, and redirected stdout/stderr logs (`codex_discord_rust.log`, `codex_discord_rust.error.log`). In the redirected trampoline path, `Start-CdrDetachedProcess` verifies the live process handle's creation ticks against `$meta.Ticks` before binding and throws if neither a verified live handle nor `$exitFile` is obtained. Installation paths containing spaces and apostrophes are safely quoted across `codex-discord-bot-headless.vbs` (`PsSingleQuote`) and `codex-discord-bot.cmd` (`$env:SCRIPT_DIR`). Ordinary MCP terminal commands remain job-contained and cleaned up on exit/cancel/timeout.
   - Every start/stop/restart/exit-all action persists its durable revisioned user intent (`Revision`, `DesiredState`, `UpdatedAtMs`, `Source`) under `.cdr-maintenance/intent.lock` BEFORE writing or clearing runtime stop markers. For `전체 종료` (`Set-CdrExitAllIntent`), a recoverable atomic decision (`.cdr-maintenance/exit-all-intent.json`) and both component intents (`bot-intent.json`, `mcp-intent.json`) are durably persisted before signaling either runtime.
   - Final spawn holds `.cdr-maintenance/intent.lock` (`Enter-CdrIntentLock`) continuously across duplicate/live-process checks (`Read-CdrComponentLaunchJournal`, `Assert-CdrNoUncertainLegacyBotLaunchJournal`, and `Get-CdrComponentObservation`), final `Revision`/`DesiredState` verification, writing `Phase = 'launching'` with default pinned `ArtifactHash`/`BuildInfo` (validated via `Get-CdrRuntimeArtifact` without swallowing malformed `--build-info` or provenance errors, and verified at startup via `Assert-CdrStartedArtifact`), calling `Start-CdrDetachedProcess`, and binding `Phase = 'launched'` with the exact child `ProcessId` and `ProcessIdentity` (without post-spawn force-kill compensation), serializing both `Invoke-CdrJournaledProcessLaunch` and `Start-RustRuntime` while long exit/readiness waits run outside the intent lock.
   - In `Stop-CdrComponentRuntime`, initial target and launch-journal observation are bound to the captured `$stopOperationRevision` and `$stopOperationDesiredState` inside `Enter-CdrIntentLock` (preserving unknown-journal holds on `launching`, `launch_outcome_unknown`, or corrupt journals), and both force-termination commitment (after the grace wait, invoking `Stop-CdrVerifiedProcess ... -WaitTimeoutMs 0` under `Enter-CdrIntentLock` so retained-handle `Kill()` executes inside the short lock while post-kill exit confirmation runs outside `.cdr-maintenance/intent.lock`) and final `Phase = 'stopped'` journal completion / manual stop marker writes re-verify under `Enter-CdrIntentLock` that the current intent revision and desired state still match `$stopOperationRevision` / `$stopOperationDesiredState` and that no newer launch journal (`launching`, `launch_outcome_unknown`, or higher revision) or live child with a different `ProcessIdentity` has superseded the stopped target (returning `Reason = 'superseded_by_newer_intent'` with 0 force-kill attempts if superseded, and also guarding the `already_stopped` branch).
   - Uncertain spawn outcomes (`launching` without verified child identity, or corrupt/unreadable `.cdr-maintenance/<component>-launch.json` or `.codex_discord_rust.restart.launch` journals) enter `launch_outcome_unknown` hold without blind retries.

4. **Single Tray & Opt-in Watchdog**
   - Single tray instance per install root, independent of bot PID, displaying both Bot and MCP status. `codex-discord-tray.ps1` is saved with a UTF-8 BOM so Windows PowerShell 5.1 parses `전체 종료` (`51204,52404,32,51333,47308`) without CP949 mojibake.
   - Tray menu provides: Bot Start, Bot Stop, Bot Restart, Bot Force Restart, Open bot log, Open bridge folder, and **Exit all (`전체 종료`)**.
   - No "Exit tray icon only" item; accidental tray UI crash/close leaves Bot and MCP running; explicit `전체 종료` (`Invoke-CdrTrayExitAll` in `codex-discord-tray-runtime.ps1`) persists stop intents for both Bot and MCP first (`$exitDecision = Set-CdrExitAllIntent -RepoRoot $resolved -Source 'tray-exit-all'`, `$expectedBotRev = [uint64]$exitDecision.Bot.Revision`, `$expectedMcpRev = [uint64]$exitDecision.Mcp.Revision`), binds each `Stop-CdrComponentRuntime` call (`-PreserveIntent -ExpectedIntentRevision $expectedBotRev` / `$expectedMcpRev -ExpectedDesiredState 'stopped'`) to the exact per-component Exit-All revisions (`R2`), stops both gracefully with the 45-second production default (`GraceTimeoutMs = 45000` across `Stop-CdrComponentRuntime`, `Request-BotStop`, `Invoke-CdrTrayExitAll`, and `Invoke-TrayExitAllAction`, pumping WinForms events while waiting and never implicitly force-killing on timeout), re-verifies under `Enter-CdrIntentLock` after both stops finish that neither component's intent revision/desired state nor launch journal/live process observation moved forward (`Reason = 'superseded_by_newer_intent'`, returning `AllStopped = $false` and `KeepTrayOpen = $true` if superseded), and retains the `전체 종료 실패` error diagnostic across `Update-TrayStatus` timer ticks if either fails to stop, is superseded, or has `unknown` process observation.
   - Opt-in watchdog (`codex-discord-watchdog.ps1`, `codex-discord-rust-watchdog.ps1`, `Invoke-CdrMcpWatchdog`) monitors Bot and MCP independently (including supervising and restarting a crashed External MCP during `Enter-RestartDrain`, asynchronous `Wait-RustThreadsQuietForRestart`, and `Wait-RustRuntimeExit`, covering both `Parallel` and existing `IgnoreNew` scheduled tasks) and honors manual stop intents.

5. **Single Release Bundle, Bot-Only Update Isolation & Safe `embedded -> external` Transition**
   - Windows x64 release bundle and prebuilt installer include `cdr-runtime.exe`, `cdr-remote-agent.exe`, and `cdr-pro-helper.exe`.
   - Bot-only binary updates (`Update-CdrBotBinaryOnly` and `Install-CdrMaintenanceCandidate`) replace only `cdr-runtime.exe` and stage candidate MCP binaries/helper scripts under `.cdr-maintenance/` while external MCP is running, never overwriting or interrupting the active MCP process or restarting a manually stopped bot.
   - Initial `embedded -> external` transition (`Invoke-CdrMcpOwnershipCutover`, default `EmbeddedExitTimeoutMs = 45000`) strictly executes:
     `validate healthy .codex_discord_rust.drain.identity (state=open + matching embedded PID) while rejecting non-open/active drain operations -> fence old CMD/helpers with .codex_discord_bot.disabled (mcp_cutover_fence), legacy control lock (.codex_discord_rust.control.lock), cutover marker (.codex_discord_runtime.cutover), legacy markers & unknown observations -> verify already-admitted legacy helpers targeting the install root (codex-discord-bot.cmd, codex-discord-bot-headless.vbs, codex-discord-watchdog.ps1, codex-discord-rust-watchdog.ps1, codex-discord-rust-restart.ps1, including relative/ambiguous helper invocations such as cmd.exe /d /c codex-discord-bot.cmd, unreadable shell command lines in the current session, or process-inventory query errors without excluding caller ancestors) have exited -> capture authorized MCP intent revision -> request restart_handoff (atomically publishing completed .codex_discord_rust.restart first and completed .codex_discord_rust.drain.prepare second via Publish-CdrCutoverDrainFenceMarkers delegating to the canonical Write-AtomicRestartMarker in codex-discord-rust-drain.ps1 same-directory temp + Move/Replace alongside bot_data/remote_mcp.stop = restart_handoff so RuntimeDrainController never observes a partial prepare or prepare-without-restart quarantine across both direct-journal and preloaded-drain entrypoints, F1, while preserving the single-use remote-mcp-restart.json project-binding payload across embedded process exit while .codex_discord_runtime.cutover is active so the replacement external cdr-remote-agent.exe claims and restores the thread->root project binding on first connect while preserving the live session-generation fence requiring a fresh ProjectSession activation; in-flight terminal/computer sessions are not promised seamless survival across process replacement, R1/R4) & confirm exact embedded owner exit -> durably persist embedded_owner_exited=true & embedded_drain_runtime_id -> start external MCP once with ExpectedIntentRevision (never clearing a Stop issued during wait) -> verify under Enter-CdrIntentLock that MCP intent still matches $authorizedMcpRevision and DesiredState = 'running' (throwing 'External MCP intent was superseded or stopped before final ownership commit' and recording reason = 'commit_write_failed:...' in cutover_failed_hold if a concurrent Stop/Exit-All or superseding revision arrived before final ownership commit, R1/R4), strict status readiness (Test-CdrExternalMcpCutoverStatusReady: strict booleans, schema, install_root, pid, process_identity, executable_path, artifact_sha256, build_info, generation >= 1, mandatory non-null heartbeat_at_ms & connection_verified_at_ms freshness within 6,000 ms and <= 2,000 ms future skew, and current bot DeviceId/BridgeFingerprint), live MCP observation, and absence of active legacy helpers -> atomically commit external ownership mode (.cdr-maintenance/mcp-ownership-state.json) BEFORE releasing .codex_discord_runtime.cutover and .codex_discord_bot.disabled (or if interrupted after commit before fence release, resume on the next Invoke-CdrMcpOwnershipCutover call to clean up leftover self-owned fences with ResumedFromCommitted = $true without spawning a duplicate MCP process; or hold in cutover_failed_hold with fences intact and without automatic rollback to embedded)`.
